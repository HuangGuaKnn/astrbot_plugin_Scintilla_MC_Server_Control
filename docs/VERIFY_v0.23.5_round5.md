# 核验记录 · v0.23.5 第五轮（外部复核整改）

> 本文件属**内部**记录（`docs/VERIFY_*` 已在 `.gitattributes` 标记 export-ignore，不进发布包）。
> 用途：把「这一轮改了什么、凭什么说改好了、哪条还是观察期」写成一份可核对的东西 ——
> 主人手里的 GPT 核验单到齐后，直接与「2. 逐条对照」并排看：对得上的打勾，对不上的按同一格式追加。
>
> 环境：Windows + AstrBot 自带 Python 3.12，本机 Edge 通道；发版门禁脚本 `run_release_verify.py`。

## 0. 一句话

第五轮修的是**越权与缺口**（精排越过禁用、切换后缺向量没人补、失败被成功覆盖、监听停不掉），
外加一处**流程**上的洞：**发版流程只跑 `test_*.py`，UI 契约类一条都没跑** —— 打 tag 可以直接绕过契约层。
现在 CI 与发版跑**同一个脚本、同一份清单**，清单只有 `tests/_ui_manifest.py` 一处来源。

## 2. 逐条对照

### A 精排越过「禁用 / 待审批 / 已删除」

| # | 复核指出的 | 旧行为现场 | 修法 | 取证断言 |
| --- | --- | --- | --- | --- |
| A1 | `_search_with_rerank()` 把 `_rank_candidates()` 的输出**整段**当候选池，被禁用 / 待审批条目照样进池、照样被精排、照样返回 | 语义通道只查「topic 在不在条目表里」，而向量索引不会因为「手工禁用」而删向量 → 精排开关一开，禁用形同虚设（关掉精排反而更严） | 进池前先按 `self._searchable()` 过滤（与 `search()` 同一口径）。**过滤必须在建 docs 之前**：精排回的 `idx` 是池下标，池一变下标与文档的对应关系就全错 | 「被禁用 / 待审批的条目**进不了精排池**」（断言进池文档数 == 1）、「结果里没有禁用 / 待审批的条目」 |
| A2 | 精排是**网络往返**，回来时条目可能已经变了：期间被禁用 / 待审批照旧返回，**被删除**的更狠 —— `_entry_view()` 直接 `KeyError`，整次检索炸掉 | 请求前的快照被沿用到结果组装 | 结果组装前**重取** `_searchable()`，池里的 topic 已不在可检索集合里就跳过 | 「等待精排期间被禁用 → 回来照样不放行」、「等待精排期间被删除 → 不崩」（旧写法当场 `KeyError`）、「也不返回已删除的条目」 |

### B 切换 / 复制 / 移动预设后「条目在、向量不在」

| # | 复核指出的 | 旧行为现场 | 修法 | 取证断言 |
| --- | --- | --- | --- | --- |
| B1 | 补算脏信号只挂在**写入**路径上，切换 / 复制 / 移动只搬条目表或换实例 —— 既没有写入也不是启动，钩子永远不响，复制来的条目**长期搜不到**（纯词法还查得到，所以不易察觉） | `_apply_active_knowledge()` 收尾只做 reload | 收尾时按 `kb.pending_vectors()` 判一次缺口，有缺口就排一次补算；判据只有 `pending_vectors()` 一处，`semantic_stats()["pending"]` 也读它 | 「切过去就排了补算」（旧写法 `touch == 0`）、「语义通道关着 → 不排（不烧额度）」、「向量齐了 → 不再重复排（幂等）」、「`semantic_stats` 与它同源」 |

### C 失败可见性（统一落盘账本）

| # | 复核指出的 | 旧行为现场 | 修法 | 取证断言 |
| --- | --- | --- | --- | --- |
| C1 | 预设文件写失败被**紧随其后**的「注册表写成功」覆盖成一切正常 | `create()` / `remove()` 都是「本地记 file_ok → `_persist_registry()` → 用它的字段整体覆盖回包」→ 磁盘满 / 只读时文件没写出来，`/state` 仍 `save_ok: true`，重启后预设凭空消失 | 落盘结果收进**统一账本** `_note_save(部件, ok, err)`；注册表与预设文件是**两个部件**、各记各的、互不覆盖，聚合值现算；某部件下次自己写成功就清自己的红 | 「失败没被紧接着的注册表写成功抹掉」（断言 `preset_file.ok is False` **且** `registry.ok is True`）、「状态接口读聚合口径」、「这个部件下次写成功 → 红被清掉」、「反方向也成立」 |
| C2 | 指纹回写失败进不了**同一次**写入响应 | `save()` 已说成功，绑定指纹的 `write_text` 失败只进日志 | 并进本次写入结果（`last_save_ok` / `last_save_error`），与第四轮「并进落盘健康度」同源 | 「指纹回写失败 → 这次写入的响应也不许说「存好了」」（只读文件现场） |
| C3 | 预设「移动」的 warning 在 WebAPI 层被丢掉 | 管理器说了「已完成复制，源预设未清空」，`transfer_preset` 的 `notice_text` 只念「已移动 N 条」 | `notice_text` 带上 `（⚠ …）`，并保留独立 `warning` 字段 | 静态：「warning 进 notice_text」+「保留结构化字段」；行为：「移动：动作仍算成功但 warning 说清源库没清干净」、「落盘字段与其它预设接口同形」 |
| C4 | —（本轮自查补的一处同源） | 上面四处都靠「谁记 last_*」拼起来，缺一处就漏 | 账本 API 只有 `_note_save` / `save_health()` 两个入口，UI 与 API 都读它 | 静态：`SAVE_PART_PRESET_FILE` / `SAVE_PART_REGISTRY` 成对出现；`create` / `remove` 各只记一次自己的部件 |

### D 日志监听的启动 / 生命周期 / 可观测

| # | 复核指出的 | 旧行为现场 | 修法 | 取证断言 |
| --- | --- | --- | --- | --- |
| D1 | `start()` **不幂等** | 重复 start（热重载 / `_restart_event_listener`）用新任务覆盖 `self._task` 句柄，旧任务没人取消、没人等待 → **永远停不掉**，还和新任务抢读同一个文件（同一条日志播两遍） | `start()` 开头 `await self.stop()` 收掉上一轮 | 「重复 `start()`：旧任务被收掉，不留在后台」（断言旧任务 `done()`） |
| D2 | 初始化定位的同步文件 IO 占着**事件循环** | `start()` 里 `exists()/stat()/读头/探编码` 全同步，正好在启动路径上（网络盘 / 大清早轮转） | 整块搬进 `_prime_state()` 走 `asyncio.to_thread` + 超时；`_poll()` 的 IO 调用统一走 `_io_wait()`（超时按「本轮没读到」降级并留痕） | 静态：`_prime_state` 走 `to_thread`、`_poll` 内 7 处 IO 全在 `_io_wait` 里；行为：「单次 IO 超时返回 `None`」、「超时留痕 `io_timeouts` + `last_error`」 |
| D3 | 没探测过却自称「文件在」 | `_file_present` 初值 `True` → 「日志文件根本不存在」在 `health()` 里表现为一切正常 | 默认 `False`，`_probed` 如实报「这一轮探测过没有」 | 「还没 `start()` → 不自称「文件在」」、「`start()` 后如实报「探测过、文件在」」 |
| D4 | 位置未知时的兜底方向 | 位置未知若从 0 开始，会把**整份历史日志当新事件重播**（比漏几条严重得多） | 位置未知 → 第一轮直接落到文件尾 | 「位置未知时不从 0 重播历史」（断言 `seen == []` 且 `_pos == 文件大小`） |
| D5 | 孤儿任务的异常没人取 | `add_done_callback(self._orphaned.discard)` 丢引用 → 异常收尾只剩一行 "Task exception was never retrieved"（连哪个任务都看不出来） | 统一走 `_reap_orphan()`：取走异常、记日志、清引用 | 「孤儿任务收尾：异常被取走且不抛」（含已取消的分支） |

### E 发版门禁（本轮最要紧）

| # | 复核指出的 | 旧行为现场 | 修法 | 取证断言 |
| --- | --- | --- | --- | --- |
| E1 | `release.yml` 的 verify 只跑 `compileall + tests/test_*.py` —— **UI 契约类在发版流程里一条都没跑** | 「本机没跑 / tests.yml 红了」都拦不住发版（跨 workflow 没有 `needs`，按 SHA 查那个 run 又常常还在排队）→ 打 tag 直接发版可绕过整个契约层 | 发版与 CI 跑**同一个** `run_release_verify.py`（静态 + 全套 `test_*.py` + UI 契约类），verify job 装 Playwright + Chromium | 静态：`release.yml` 含验证脚本与 `playwright install`、`tests.yml` 的回归 job 是 `--no-ui` |
| E2 | 三档清单在两处各写一份，迟早分叉（分叉方向永远是「新用例漂进没人管的软门禁」） | `tests.yml` 里硬编码 `HARD_UI` / `SOFT_UI`，发版流程再抄一份 | 三档归类唯一来源 `tests/_ui_manifest.py`，workflow 用 `--emit-env` 现算进 `$GITHUB_ENV` | 「`--emit-env` 只输出环境变量行」（2 行，混日志即污染 `$GITHUB_ENV`） |
| E3 | 旧守卫只看 `*_check.py` | 诊断脚本 `ui_theme_flash_trace.py` 不叫 `_check` 就绕过了守卫 | 守卫覆盖**全部** `ui_*.py`，未归类即红 | 「没有未归类的 `ui_*.py`」、「取证脚本也被清单收编」 |
| E4 | 跑测循环自身两个隐患 | ① 一次性 `subprocess.run()` **没有超时** → UI 用例挂死时整条命令再也出不来结果（比「红」更糟，把流水线一起拖住）；② 超时只杀父进程 → 浏览器孤儿继续占端口，下一个用例跟着倒 | 逐文件超时 + 超时后 `taskkill /T`（非 Windows 用 `killpg`）+ 把超时**记为失败** | 「挂死的用例被超时掐掉并记为失败」（造一个死循环用例真跑） |
| E5 | 两份跑测实现 | `run_v0230_all.py` 与 workflow 各有一套循环，新隐患只修在一边 | `run_v0230_all.py` 瘦成一行包装，共用 `run_release_verify.py` 的循环（本机全量仍跑**全部** UI，含观察期与取证） | 「本机全量复现脚本共用同一套循环」、`--plan` 真跑 |

## 3. 遗留项（观察条件写在这里，到点由主人拍板）

1. **UI 观察期四件（`ui_card_layout_check` / `ui_kb_fold_check` / `ui_select_option_check` / `ui_sw_wrap_check`）**
   —— 判据含像素阈值（等高 / 顶边对齐 / 内容高度上限 / 行盒 / 原生下拉配色），
   在 Linux + 自带 Chromium 与本机 Windows + Edge 上不完全一致。观察条件：CI 上连续几轮绿灯后删掉
   `ui-render` job 的 `continue-on-error`。
2. **发版 verify 只跑硬门禁 9 件**：观察期 4 件与取证脚本 1 件本机跑全、CI 的 `ui-render` 也跑观察期，
   发版前置暂不跑它们（它们本来就不阻断，跑等于白等 5 分钟）。可讨论是否改为「发版只跑硬门禁 + 记录结果」之外的方案。
3. **`_io_wait` 的 15 秒上限是拍的**：超时按「本轮没读到」处理（下一轮继续），
   真正的判据是「`stop()` 的 5 秒承诺要真」。若线上出现「日志被别的进程长时间独占」的报告，再按现场调。
4. **`health()` 新增的 `probed` / `io_timeouts` 只进了 `/api/.../health`**，设置页未做可视化；
   要不要在知识库页那排健康度旁边显示「日志监听：已探测 / N 次读盘超时」由主人决定（本机无该需求，故未自行加）。
5. **本轮未做的两处（明确记账，不装没看见）**：
   - `correct_entry()` 之后**没有**强制重算向量（现在靠「内容变更 → 发脏信号」这条链，已由第四轮修好；
     但「管理器级校正」若绕过 `save()` 仍会漏 —— 当前没有这样的调用方）。
   - `_rank_candidates()` 本身仍只按「在不在条目表里」过滤，靠 `search()` / `_search_with_rerank()`
     各自收口；**没有**把它改成内部过滤（改动面更大，收益是省一次 filter）。若 GPT 单子认为应下沉，
     按新单子做，别在这一轮悄悄改。

## 4. 这一轮的教训

- **「同一份事实必须只有一处来源」** 这条在本轮出现了三次：精排池（越权）、落盘账本（失败被覆盖）、
  清单与跑测循环（门禁绕过）。三处的共同点都是**同一件事有两个说法**，而两个说法迟早不一致。
- **最危险的洞不在代码里，在流程里**：E1「发版只跑 test_*.py」意味着前四轮的整改结果
  **没有任何东西保证它随版本一起存在** —— 契约层可以整层丢掉而发版照样成功。
  这也是本轮唯一花时间改 CI/发版配置的一处。
